# Proposal

## Why

对应开发文档里程碑 M6。M5 之后 Manager 能打分、能按权重选节点、能记在途账，但节点只有“能选 / 不能选”两种情况：

- 失联或关键指标越限的节点被排除，回来后立刻按满权重接任务，没有预热。
- 只有上报通道在看节点，接任务的 50052 端口坏了（灰色故障）Manager 看不出来。
- 执行超时多的节点被 f_timeout 压到几乎选不中，但没有办法确认它是否已经恢复，只能等 T 按 10 分钟半衰期慢慢衰减。

开发文档用一个四状态的熔断器解决这些问题：正常（闭合）、剔除（断开）、急救（半开）、慢启动。本变更实现它，验收标准是故障注入表里的节点类故障全部符合期望。

## What Changes

- **节点状态机**（`manager/breaker/`）：每台节点一个状态，正常、剔除、急救、慢启动，六条转移：
  1. 新节点 → 慢启动。
  2. 慢启动 → 正常：满 5 分钟。慢启动期间 f_slow 从 0.2 线性升到 1.0，f_inflight 固定为 1，只积累基线。
  3. 正常 → 急救：选中概率低于 0.5/N、score ≥ 0.6、f_timeout 是各因子里最小的，并且已过退避间隔。
  4. 急救 → 慢启动：急救结束时节点仍新鲜；否则进入剔除。
  5. 正常（或慢启动）→ 剔除：失联 3 秒、关键指标越限、低频探测连续 3 次失败、最近 5 分钟未确认比例超过全体均值 3 倍（至少 20 个样本）。失联的节点不急救。
  6. 剔除 → 慢启动：重新上报、关键指标连续 5 次正常、最近一次探测成功；按新节点对待，清空在途基线和超时计数。
- **低频探测**：Manager 新增探测线程，每秒对每台新鲜节点异步调用一次 `WorkerTask.Probe`（截止 500 ms），连续 3 次失败剔除。
- **急救**：
  - Manager 每个急救中的节点一条 `Rescue` 双向流（单独的 channel 和线程），每 1 ms 发一条带 seq 和发送时间的请求；待确认队列先进先出，只看队头判单次超时（10 ms），迟到回应按 seq 丢弃，连续一段超时算一次网络事件。
  - 每 100 ms 结算一批：全部成功则 T × 0.9；有失败则目标下调为 `1/N − ε·(2ᵏ − 1)`（k 为连续失败批数，下限 0）。选中概率达到目标或急救满 10 秒就关闭流。
  - 反复急救按 5、10、20 … 60 分钟指数退避，退避次数以 1 天为半衰期衰减。
  - Worker 实现 `Rescue`：第一条请求到达时把 cpustat 刷新周期改成 1 ms，每条请求重新读一次 CPU 并回一条样本，流结束（或超过 15 秒上限）时改回原周期。同一时刻只接受一条急救流。
- **Redis**：`node:{id}` 增加 `state`、`state_reason`、`state_since_ms`、`f_slow`、`probe_fail_streak`；状态变化时立即写一次（不必等下一次上报，失联节点也能看到状态变成剔除）。
- **配置**：`manager.yaml` 增加 `breaker` 段；`worker.yaml` 的 `task` 段增加 `rescue_max_s`。

## Capabilities

### New Capabilities
- `manager-node-state`：四个状态、六条转移、各状态下的候选资格与因子（f_slow、慢启动期间 f_inflight 为 1）、剔除条件（含灰色故障）、恢复条件、状态写入 Redis。
- `manager-probe`：低频探测的周期、截止时间、连续失败计数与剔除、对哪些节点探测。
- `manager-rescue`：急救的触发条件、退避、双向流协议、单次超时与网络事件、批结算、目标下调、结束条件。
- `worker-rescue`：Worker 端 `Rescue` 的行为：刷新周期切换与恢复、每条请求一份新样本、单流限制、时长上限。

### Modified Capabilities
- `manager-scoring`（m5a）：失联与关键指标剔除不再只是 `select` 时的过滤条件，而是驱动节点进入“剔除”状态；恢复后进入慢启动而不是立即回到候选。
- `manager-allocation`（m5a/m5b）：候选集合改为“状态为正常或慢启动”；权重中的 f_slow 不再恒为 1。
- `worker-task-exec`（m5b）：`Rescue` 不再返回 `UNIMPLEMENTED`。

以上都以 ADDED 增量写新要求，归档时合并。

## Impact

- 对应里程碑：M6。影响模块：manager（新增 `breaker/`，改 `ingest/node_table`、`inflight/`、`scheduler_loop`、`storage/`、`main.cpp`）、worker（`task/` 增加急救，`collector` 暴露最新样本）、config、tests、deploy 文档。
- proto 不改：`Rescue`、`Probe`、`RescueReq/Resp` 在 M1 已定义。
- Redis：`node:{id}` 多 5 个字段；状态变化时额外写一次 HSET（很少发生）。MySQL 不涉及。
- 调度锁：状态机每 100 ms 持锁遍历一遍节点（≤ 20 台），探测结果每秒每节点一次加锁，急救每 100 ms 一次加锁结算。都是微秒级。
- 网络：低频探测每节点每秒一个小 RPC；急救期间每秒 1000 条请求和回应（每条回应带一份样本，约 200–400 字节），最长 10 秒。
- Worker：急救期间 cpustat 刷新周期为 1 ms（M2 已验证 1 ms 周期长时间运行无警告），每条请求读一次共享页（约 12 ns）。
- 行为变化：任务服务没开启的 Worker 会因为探测失败被剔除，不再接任务（它本来也接不了）。
- 不在范围内：
  - AI 预测因子 f_pred（M9），仍为 1。
  - 状态变化事件写 `stream:events`、推给看板（M7）。
  - 对照实验调参（M10）。
