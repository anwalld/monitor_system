# Design

## Decisions

1. **用 Manager 的在途账判满，而不是 Worker 上报的运行数**：在途账在 `Allocate` 的同一把锁里加一，并发突发时也不会超发；上报有 1 秒延迟，一秒内 8 个任务就能把 2 核容器的 4 个名额占满。在途账包含已分配未发送、已发送未确认、运行中三种状态，比 Worker 实际运行数略多（偏保守）；作废、完成、失败、执行超时都会销账。
2. **硬条件，只在选择时生效**：满载是瞬时的容量约束，不是节点故障。所以不乘进权重公式、不改 `factors_for`，`tick_states` 里的选中概率和急救触发照旧（否则满载节点概率为 0 可能误触发急救）。
3. **对照策略不加**：`rr`、`wrr` 代表不感知负载的负载均衡器，加上就不是原来的对照了。
4. **上报的上限**：取任务服务解析后的 `max_concurrent`（配置为 0 时是 2 × 核数）；任务服务关闭时为 0。

## Risks / Trade-offs

- 全部候选都满时直接拒绝，失败从 `Submit` 移到 `Allocate`，总数未必减少；减少的是“有空闲节点却派给满载节点”的那部分。复跑结果会说明。
- 在途账偏保守：客户端拿到分配后不发送，名额要等 30 秒作废才释放。

## 实现中的决定

1. **虚拟机 Worker 直接换二进制**：`install-worker.sh` 会装包、重编 cpustat 模块，这次只换 `/opt/lm/bin/worker`（旧版留作 `worker.m10`）后重启服务。
2. **复跑只跑三组**：预测推送关闭时 `score` 与 `score_nopred` 等价，去掉 `score_nopred`，30 次约 90 分钟。
3. **全部满载时的失败是预期行为**：三台同时满（虚拟机被 ROS 占着时常剔除，两个 2 核容器各 4 个名额）时 `Allocate` 拒绝，比派给满载 Worker 再被拒更快、也不打扰 Worker。要进一步减少，需要排队或更多节点，不在本变更范围。
